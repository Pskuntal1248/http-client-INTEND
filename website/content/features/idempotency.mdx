# Idempotency & Retry

<Callout type="info">
POST, PUT, and PATCH requests are protected automatically with idempotency keys and bounded retries.
</Callout>

## Why It Matters

If a write request succeeds server-side but the response is lost, retrying without idempotency can create duplicates. Intend avoids this by reusing the same key on automatic retry.

## Request Safety Rules

| Rule | Behavior |
|---|---|
| New send intent | Generate fresh UUID key |
| Auto retry for same intent | Reuse exact same key |
| Manual force new send | Create new key regardless of history |

## Retry Policy

| Failure type | Retry |
|---|---|
| Connection timeout/refused | Yes |
| DNS resolution failure | Yes |
| HTTP 502 | Yes |
| HTTP 503 | Yes |
| HTTP 504 | Yes |
| HTTP 4xx | No |
| HTTP 2xx | No |

Backoff schedule:

| Retry attempt | Delay |
|---|---|
| 1 | 1s |
| 2 | 2s |

## Headers Added

| Header | Value | Purpose |
|---|---|---|
| `Idempotency-Key` | UUID v4 | Server duplicate protection |
| `X-Request-ID` | same UUID | Log and trace correlation |

## Internal State

```text
fingerprint = METHOD + ":" + URL
```

State storage: `~/.intend/intend-state.properties`

<Callout type="warning">
Persistent key state means retry safety is preserved even after app restart.
</Callout>

## Operational Checklist

<Steps>
### Send write request

Inspect outgoing headers after send.

### Observe retries

On transient failures, verify same `Idempotency-Key` is reused.

### Confirm traceability

Use `X-Request-ID` in backend logs for request correlation.
</Steps>
